Building Convexa: a compile-time architecture for conversational agents

A product teardown of the system I own at Nagent AI: the architecture, model, cost and go-to-market decisions behind it.

Hariharan V (Hari)  |  Senior Product Manager, Nagent AI  |  linkedin.com/in/vhharan1

See Convexa live: app.convexa.nagent.ai  |  More of my work: haribuilds.com

The problem

Convexa is a conversational execution agent - an AI chat agent, in the term most people use - that a company embeds on its website to talk to its visitors, whether it sells to consumers or to other businesses. It does not just answer questions: it qualifies a lead, writes the result back to the CRM, and hands off scheduling, inside one conversation.

When I took it over it was positioned as a "RAG knowledge chatbot": upload documents, get a bot that answers from them. That category is crowded, it is commoditising fast, and its buyers churn the moment a cheaper option ships. The two competitors we lost deals to both had a specific, repeated complaint in their public reviews: the bot confidently makes things up.

So I made two bets:

  1. Reposition from "answers questions" to "finishes a job." Qualify, sync, hand off - a measurable outcome, not a transcript.
  2. Make not-hallucinating the wedge. Turn the thing customers complain about into the thing we are unambiguously best at.

Everything below follows from those two bets.

The core design: one compiled prompt per customer, assembled at deploy time

A customer never writes a prompt. They answer functional questions in a one-screen onboarding flow ("what should the assistant do? capture leads? resolve issues? both?"). The backend turns those answers into a single system prompt by concatenating fixed blocks:

FINAL SYSTEM PROMPT =
    core guardrails            (identical for every customer, never edited)
  + brand and tone             (merge fields from onboarding: name, voice, languages)
  + admin's custom guardrails  (free text - validated against core before it is accepted)
  + 1-3 intent modules         (from a fixed set of 8: inform, support, qualify,
                                book, account, intake, feedback, promote)
  + 0-N custom intent modules  (compiled on demand when the fixed 8 do not cover a goal)
  + fallback policy            (per active job, a few admin toggles)
  + engagement policy          (idle-visitor re-engagement)
  + an intent router           (added only when 2+ intents are active)

The prompt is recompiled every time an admin changes a setting, and each compiled version is stored, so a deployment is a specific, inspectable artifact rather than a text box someone edited live.

Why modules instead of a per-customer prompt

The obvious alternative - a prompt-engineer tunes a bespoke prompt per customer - does not scale and does not stay safe. Every hand-written prompt is a place a guardrail can be accidentally dropped, and every change is a regression risk nobody can see.

The tradeoff I accepted: a module system is less expressive than a free hand. A customer with a genuinely unusual job has to either fit one of the eight intents or get a custom module compiled (which is validated the same way). In practice a real deployment uses one to three intents, so the ceiling has not bitten yet. What I bought for that constraint: a new customer goes live in about 10 minutes, and no customer can ship a prompt that violates a core rule.

Runtime: what happens to one visitor message

The compiled prompt is the deploy-time half of the system. This is the per-message half - seven steps between a visitor hitting send and the first word appearing. The prompt tells the model what it should do; the code steps around it make sure that is actually what happens.

  • Input checks. Every message is screened for prompt injection before it reaches the model, and personal data is redacted before it is logged or sent to a model provider. The core guardrails also tell the model to resist injection; the filter means that is not the only line of defence.
  • Query rewrite. Visitors write "and how much is that one?", which is useless as a search query. A rewrite step turns the message plus recent turns into a standalone query before retrieval.
  • Hybrid retrieval, then rerank. Keyword (BM25) search catches exact product names, SKUs, and policy terms; semantic search catches paraphrases. Both run over a vector index (Pinecone) scoped to that one customer, and a reranker keeps only the few chunks that genuinely answer the question, so the model reads less and guesses less.
  • Generate. The chat-tier model gets the cached compiled prompt, the reranked chunks, the last 5 turns verbatim, a running summary of anything older, and a stored profile for returning visitors - which is how a returning visitor gets greeted by name without replaying their old transcript.
  • Output grounding check. Before a reply is sent, its claims are checked against the chunks that were retrieved. An answer that is not supported does not go out; the agent falls back to the decline-with-a-next-step rule below instead.
  • Stream and act. The reply streams token by token, and any action - such as pushing a captured lead to the CRM - runs through connected tools.

Decision: a three-level guardrail precedence, with validation before anything goes live

Rules resolve in a fixed order:

Core Guardrails  >  Admin's Custom Guardrails  >  Intent Module defaults

Core guardrails are prepended verbatim to every deployment and cover identity and prompt-injection resistance, grounding, scope, safety and escalation, always-available human handoff, and a "never go silent" rule. An admin's own guardrails can restrict further - never loosen. That is not a convention we hope holds; every custom guardrail an admin writes is checked against the core set before it is accepted, and a custom intent module is checked the same way because it is also admin-authored free text heading into a live prompt.

Why this mattered enough to build: the demo that wins B2B deals is "type your own rule and watch it take effect." The demo that loses the renewal is the one where a customer's well-meaning rule quietly disabled the safety layer. Validation-before-live lets us keep the first demo without the second outcome.

Decision: strict grounding as the wedge, with a hard rule against dead ends

The agent answers only from the connected knowledge base, the current conversation, and explicitly connected tools. If the answer is not in one of those, it says so - it does not guess prices, dates, stock levels, or policy. The dashboard can show a "Grounded" tag on answers that are backed by real content, and the phrasing of "I don't have that" is varied so it does not read like a canned line.

The part I care most about: a bare "I don't know" is treated as a failure, not a safe default. The proactivity rule in the core guardrails forces every decline to name a next step in the same breath - an alternative source, a handoff, or a clarifying question. There is one deliberate exception (a "log my issue and leave me alone" intake mode), which is a named, scoped choice rather than a hole in the rule.

The fallback order when the knowledge base comes up empty is explicit: say so plainly, then - only if the business has switched it on - check a short allowlist of trusted outside sites (a retailer's shipping carriers, for example), then hand over a real contact. The one job that skips the outside search is issue resolution: when the agent is trying to fix a customer's actual problem, a guessed fix is worse than no fix, so it escalates to a human straight away.

This is the difference between "safe but useless" and "safe and still moving the conversation forward," and it is why I think of grounding as a growth feature, not a compliance feature.

Decision: an eval suite that gates every prompt release

Because the prompt is assembled from shared modules, a change to one module can regress every customer that uses it. So no prompt change ships without passing a golden-dataset evaluation: a fixed set of representative conversations, each with an expected behaviour (answer from a document, say "I don't know," call the CRM tool, refuse, escalate), scored by a mix of deterministic checks and an LLM-as-judge rubric. Regression against the previous version blocks the release. A separate adversarial set - prompt-injection attempts, jailbreaks, out-of-scope asks - has to pass clean.

Alongside the gate, a Test & Simulate sandbox lets the team and each customer run full multi-turn conversations against a draft assistant before it goes live, without using up their conversation allowance.

This is the least glamorous part of the system and the one that lets me change a shared module without holding my breath.

Decision: onboarding is functional questions, not prompt writing

The version I inherited had an eight-step configuration wizard. Most people did not finish it. I cut it to a single intent-capture screen - the admin picks what the assistant should do, and reaches a clear picture of the assistant's scope in under four clicks. Everything the old wizard asked is still asked, later, in context, with a working assistant already in front of the user to react to. I benchmarked 16 competitor onboarding flows before settling on this; the ones that converted best all deferred configuration until after first value.

Decision: price on the outcome, and only gate the outcome

Pricing is three self-serve tiers plus a custom Enterprise tier, billed per conversation, not per seat - unlimited teammates share one workspace. A $1 trial gives the full entry plan for 14 days.

Two calls I had to defend:

  • Per conversation, not per seat. Seat pricing punishes the customer for adding teammates, which is the opposite of what you want for a support tool. Per-conversation pricing tracks the value delivered and makes the metered-billing quota the same number the customer already cares about.
  • Gate deploy, not the product. Engineering proposed 403-gating every page and API for an unpaid workspace. I scoped the paywall to a single action: pushing the assistant live on the real site. An unpaid or lapsed workspace can build, test, and simulate the entire assistant - they just cannot deploy it until they pay. Prospects reach the value before they hit the wall, which is the whole point of a product-led motion.

Integration model

CRM sync runs through Composio rather than a hand-rolled integration. When a visitor shows buying intent, the agent captures them as a lead in the background, without stopping the conversation to make them fill in a form, and pushes the lead to the CRM automatically: routing rules, a deal-versus-ticket split, and sentiment and lead-quality scoring written back to the record. If an automatic push fails, a manual "Create Lead" retry appears on that conversation, so a lead is never silently lost. A per-conversation quota feeds metered billing.

Next on the roadmap: image, voice, and video input, voice conversations, calendar booking, live human takeover as a staffed queue, a governed-autonomy (L0-L4) selector, CRMs beyond the first, and channels beyond the website widget.

Data handling

Each customer's knowledge base lives in its own isolated index, so retrieval for one customer can never surface another customer's content. Customer data is not used to train models. Personal data is redacted before it is logged or sent to a model provider (the input check above), which also keeps it out of any vendor that a failover routes to.

Decision: treat latency as a product feature, not an infra afterthought

For a chat-shaped product, the gap between a message and a reply is felt the same way a person going quiet mid-conversation is felt. The metric that matters here is time-to-first-token (TTFT) - how long before the visitor sees anything happen, not how long the full answer takes to finish generating. Early on that gap was 4.7 seconds median - technically correct answers, slow enough to feel broken. Four changes got it to 1.2 seconds, and none of them traded quality for speed:

  • Migrated the knowledge base from plain PDF/TXT to JSONL with metadata tags - the structure that lets the hybrid BM25 + semantic retrieval filter precisely instead of scanning loosely-structured text. This improved answer quality at the same time it improved speed; the two are usually framed as a tradeoff, and here they were not.
  • Bounded conversation context to the last 5 turns instead of replaying the full transcript on every message. Anything older is folded into a running summary, and what matters about a returning visitor lives in their stored profile, not in raw chat history.
  • Cached the compiled system prompt - core guardrails, brand and tone, intent modules - so it is built once per deployment and reused, not reprocessed on every single message. This is also the one change that cut cost, not just time.
  • Switched to streaming responses - the reason TTFT, not full-answer completion time, is what a visitor actually feels.

Decision: match the model to the job, and never depend on one vendor

Convexa makes two very different kinds of LLM call, and treating them as one workload would have meant overpaying on one or underperforming on the other.

  • Tier 1, scope prompt generation. Turning a customer's onboarding answers into their scope prompt. It runs rarely, but everything downstream inherits its quality: it needs deep reasoning, strict instruction adherence, enforcement of negative constraints ("never allow X unless Y"), and clean structured JSON output.
  • Tier 2, live chat. Every visitor message. It runs constantly, so it has to be fast to first token, cheap per turn, warm in tone, and good at holding multi-turn context and calling tools.

So I made two separate calls. Different LLMs for the two prompts - the strongest reasoning model for the scope prompt, where quality compounds, and a small, fast model for chat, where volume does. That split is where the cost saving comes from. And fallbacks for performance - each tier gets two fallback models from different vendors, so a rate limit, outage, or slow response at one provider never degrades or takes down the assistant.

Cost comes from the split between the two prompts. The chat models cost more than an order of magnitude less per token than the frontier models, and chat is where almost all the tokens are - so the expensive model only runs on the one job that needs it, and the high-volume job runs on the cheap one.

Performance comes from the fallbacks. They are not there to save money; they are there so the assistant keeps performing when the primary cannot. Each one is chosen to hold up on what its tier needs most - reasoning and rule-following for the scope prompt, speed, tone, and tool calling for chat - so a failover keeps the quality bar instead of just keeping the lights on.

Three design rules sit around the chain:

  • Cache-friendly prompt ordering on all three vendors. Static content - core guardrails, scope rules - always comes before the visitor's message, so prompt caching hits on OpenAI, Anthropic, and Google alike (cached input is 90% cheaper on each, and faster). A fallback that misses the cache would be slower exactly when speed matters most.
  • Grounding does not change with the model. Each model has a different knowledge cutoff, so answers are grounded in live retrieval rather than whatever the model remembers. Failing over to an older model must not mean a staler or more made-up answer - the same wedge as the grounding decision above.
  • Models are roles, not names. Each slot in the matrix is defined by what it must be good at, and scored on benchmark fit, price, and deprecation date. Models retire and new ones ship every few months, so swapping a model is a re-score and an eval run against the golden dataset, not a redesign - and a fallback that is about to be retired is flagged early, because a fallback you are about to lose is not really a fallback.

The target is 99.99% availability for the assistant, with no single vendor able to cause an outage. Failover is specified to switch vendors in under 300ms on a 429 or 500 error without losing conversation state.

Unit economics: what one conversation costs

Per-conversation pricing only works if I know what a conversation costs to serve. I modelled it against the entry plan: $29 a month for 50 conversations, or about $0.58 of revenue per conversation.

Assumptions, per conversation: 8 visitor turns. Per turn, about 4,000 tokens of cached compiled prompt, 3,000 uncached tokens (reranked chunks, last 5 turns, summary, the message), and 250 output tokens, plus a small query-rewrite call and the output grounding check. The scope prompt is compiled with a frontier model at about 20,000 tokens in and 5,000 out, and recompiled about 4 times a month as the admin edits settings. Rates per million tokens: chat model $0.20 in, $0.02 cached, $1.25 out; chat fallback $0.80 / $0.08 / $4.00; frontier model $5.00 / $0.50 / $30.00.

Three things this told me:

  • The tier split is the margin. Running chat on the frontier model would spend about 62% of the entry plan's revenue on LLM calls alone. Tiered, it is about 6%, and even a full month running on a fallback stays under a fifth.
  • On a small plan, the scope prompt is the bigger line. A few frontier compiles a month cost more than all 50 conversations combined. That is fine because it happens a handful of times, and it is the strongest argument for keeping frontier calls at compile time and never putting one in the per-message path.
  • Prompt caching carries the chat cost. The compiled prompt is the largest block in every turn; caching it is why a turn costs a fraction of a cent.

Results

First paying enterprise customer, a deal I ran end to end from proof-of-concept through security review:

  • ~1.2s median time-to-first-token (TTFT) (down from ~4.7s)
  • ~10 minutes from onboarding to a live, deployed assistant
  • 500+ conversations handled, with under 10% unanswered (where "unanswered" means the agent explicitly could not help and escalated, not a wrong answer)

What did not work

  • The eight-step setup wizard. Most people did not finish it. Asking for every setting before the customer had seen a working assistant front-loaded all the effort before any of the value. Replaced by one intent screen, with everything else asked later, in context.
  • A PDF/TXT knowledge base. Loosely structured text gave retrieval nothing to filter on, so it pulled in loosely related passages - slower and less accurate at the same time. Moving to JSONL with metadata tags fixed both.
  • Replaying the full transcript every turn. It felt like the safe way to keep context, but every long conversation got slower and more expensive with each message. The last 5 turns plus a running summary kept the context that mattered at a fraction of the tokens.

What I would do next

  1. Put simulated conversations in the release gate. Automating the multi-turn simulations - a model playing the visitor across whole conversations, run several times per case and scored on whether the agent succeeds every time, not just once - would catch the multi-turn failures a single-exchange eval misses.
  2. Close the loop on unanswered conversations - route every "I don't know" into a weekly knowledge-base gap report, so the number that matters most has an owner and a workflow, not just a dashboard tile.
  3. Ship the autonomy selector. Right now the agent's boldness is fixed per job; customers in regulated spaces want a dial, and an approvals queue behind it.
  4. A second CRM. The Composio layer makes this mostly a config and eval problem rather than an integration rewrite, which was part of why I chose it.
